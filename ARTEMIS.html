Section 01

What is ARTEMIS?

An Android automation framework that converts natural language instructions into reliable, executable actions on real Android devices.

🧠

Natural Language Input

You write plain English instructions. ARTEMIS understands them and figures out how to execute them step by step — no scripting required.

📱

Real Device Control

Drives actual Android devices or emulators via ADB. Everything you see happen on screen is a real interaction — not a simulation.

🔗

MCP Integration

Exposes 5 tools via the Model Context Protocol, letting AI assistants like Claude Code drive your device directly from the IDE.

⚡

Two Execution Profiles

Flash: Fast reactive loop (3–5s/step) for simple tasks. Pro: Multi-agent planning and verification (15–40s/step) for complex workflows.

🎯

Dynamic-First Targeting

Uses the accessibility tree first for precise element targeting, with visual/coordinate fallback for custom UIs like Flutter canvas.

📊

Multi-Model Support

Works with Gemini, Claude, GPT-4o, and Qwen-VL. Switch the underlying vision model in artemis.jsonc without changing your tests.

Section 03

How ARTEMIS Sees the Screen

Three-layer perception system — prioritizing structured data over visual inference for speed and accuracy.

🌳

Layer 1 — Accessibility Helper

An Android Accessibility Service installed on the device. Reads the full UI tree as structured XML — element class, text, bounds, resource-id, clickability. Fastest and most accurate.

🔧

Layer 2 — UIAutomator2

Standard Android tool that dumps the UI hierarchy. Used as a fallback if the Accessibility Helper is disabled or unavailable. Slightly slower but same concept.

👁️

Layer 3 — Visual / OCR

Last resort: captures a screenshot and sends it to a Vision LLM (Gemini/GPT-4o) to identify element coordinates. Used for Flutter canvas, custom Compose, and any surface not in the tree.

What the Accessibility Tree Looks Like

xml — accessibility tree dump
<hierarchy>
  <node index="0" text="Welcome Back"
        class="android.widget.TextView"
        bounds="[0,100][1080,180]"/>

  <node index="1" text="" hint="Email address"
        class="android.widget.EditText"
        resource-id="com.myapp:id/email-field"
        clickable="true"
        bounds="[24,220][1056,300]"/>

  <node index="2" text="" hint="Password"
        class="android.widget.EditText"
        resource-id="com.myapp:id/password-field"
        clickable="true"
        bounds="[24,320][1056,400]"/>

  <node index="3" text="Sign In"
        class="android.widget.Button"
        resource-id="com.myapp:id/login-button"
        clickable="true"
        bounds="[24,440][1056,520]"/>
</hierarchy>
💡

Dynamic-First, Coordinate-Fallback

ARTEMIS always tries to use element indices from the accessibility tree first (fast, precise, doesn't break on UI scale changes). Only if an element isn't in the tree does it fall back to screen coordinates from the vision model (slower, more expensive).

Section 04

How ARTEMIS Understands & Executes

From your plain-text instruction to a real tap on the screen — every step explained.

The 5-Phase Execution Loop

✍️

Phase 1 — You Write the Task

Plain English: "Login with test@email.com / Pass123, verify dashboard loads". No special syntax, no formatting rules — just describe what you want.

🏗️

Phase 2 — ARTEMIS Builds the Context

Assembles 4 layers into one LLM message: System Prompt (instructions for the agent) + Your Task + Current UI Tree XML + Screenshot + Compressed History of previous turns.

🧠

Phase 3 — LLM Reasons and Returns ONE Action

The vision LLM (Gemini/Claude) reads everything and responds with a single JSON action. Always one action per turn — never a batch.

⚙️

Phase 4 — ARTEMIS Translates to ADB

Parses the JSON, finds the element in the tree, calculates center coordinates, and sends the ADB command to the device.

🔄

Phase 5 — Observe Result and Repeat

Captures a new screenshot and UI tree, checks if the action worked, adds the result to history, and loops back to Phase 2 — until task is done or max turns reached.

What the LLM Actually Receives Each Turn

llm input — assembled each turn
// ── LAYER 1: System Prompt (fixed every turn) ──
You are ARTEMIS, an Android automation agent.
Respond ONLY with valid JSON in this exact format:
{
  "thought": "your reasoning here",
  "action": "tap|swipe|type|scroll|back|home|wait|done|fail",
  "target": { "index": 3, "resource_id": "..." },
  "value": "text to type (if applicable)"
}

// ── LAYER 2: Your Task ──
TASK: Login with test@email.com / Pass123, verify dashboard
PROFILE: flash | MAX_TURNS: 30

// ── LAYER 3: Current UI State ──
<hierarchy>
  <node index="1" text="" hint="Email" class="EditText"
        resource-id="com.app:id/email" clickable="true"/>
  <node index="2" ... />
  <node index="3" text="Sign In" class="Button" clickable="true"/>
</hierarchy>
[SCREENSHOT: base64 image attached]

// ── LAYER 4: History (compressed) ──
Turn 1: opened_app → success, saw login screen
Turn 2: tapped(index=1, email_field) → focused

What the LLM Returns

json — llm response (one action per turn)
{
  "thought": "Email field is at index 1 with resource-id email-field.
             I need to tap it first, then type the email address.",
  "action": "tap",
  "target": {
    "index": 1,
    "resource_id": "com.myapp:id/email-field",
    "text": "Email address"
  },
  "value": null
}
⚠️

Two LLMs Working Together

There are actually two LLMs involved: (1) The outer LLM (Claude Code / Windsurf) decides to call ARTEMIS and what task to give it. (2) The inner LLM (Gemini/Claude inside ARTEMIS) decides each individual action on screen. They're completely separate.

Section 05

The ADB Execution Layer

Every action ultimately becomes an ADB command sent from your host machine to the Android device.

adb — action translations
# Tap an element
adb shell input tap 540 1200

# Type text
adb shell input text "hello@gmail.com"

# Swipe (scroll down)
adb shell input swipe 540 1500 540 500 300

# Press back
adb shell input keyevent KEYCODE_BACK

# Press home
adb shell input keyevent KEYCODE_HOME

# Start app
adb shell am start -n com.pkg/.MainActivity

# Capture screenshot
adb shell screencap -p /sdcard/s.png
adb pull /sdcard/s.png ./screenshot.png
⚡

Action Burst

For rapid sequential actions (e.g. swipe + tap on a tooltip that appears for 1 second), ARTEMIS executes them as a single burst without waiting for a new LLM turn. Beats transient UI timing.

🎯

Coordinate Calculation

When an element is found in the accessibility tree, ARTEMIS calculates its center point from the bounds attribute and uses that for the ADB tap command — never hardcoded coordinates.

✅

How Coordinates Are Calculated

If element bounds are [24,440][1056,520], center X = (24+1056)/2 = 540, center Y = (440+520)/2 = 480. ARTEMIS sends adb shell input tap 540 480.

Section 06

The MCP Protocol — Deep Dive

Model Context Protocol: the standardized bridge that lets AI assistants call external tools like ARTEMIS.

Why MCP Exists

Before MCP, every AI tool integration was custom-built. MCP is the USB-C of AI integrations — one standardized protocol that works with any compatible tool and any compatible AI assistant. ARTEMIS implements MCP natively, so Claude Code, Cursor, Windsurf, and Codex can all drive your Android device with zero custom code.

The 3 Layers

🖥️

HOST

The application you're using — Claude Code, Cursor, Windsurf. It contains the MCP client and manages connections to MCP servers.

🔌

MCP CLIENT

The internal component inside the host that speaks JSON-RPC 2.0 to MCP servers. Handles discovery, execution, and progress notifications.

⚙️

MCP SERVER

ARTEMIS. Exposes tools the AI can call. Runs locally as a child process (stdio transport) or remotely via Streamable HTTP.

The Complete Lifecycle

🤝 Step 1 — Initialization (Handshake)
json-rpc — handshake
// Claude Code → ARTEMIS
{
  "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "clientInfo": { "name": "claude-code", "version": "1.0.0" },
    "capabilities": { "sampling": {} }
  }
}
// ARTEMIS → Claude Code (agrees on version + capabilities)
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "protocolVersion": "2025-11-25",
    "serverInfo": { "name": "artemis-mcp", "version": "1.0.0" },
    "capabilities": { "tools": {} }
  }
}
🔍 Step 2 — Discovery (What tools exist?)

Claude Code asks for all available tools. ARTEMIS responds with full schemas — including which parameters are required vs optional, and what types they expect.

json-rpc — tools/list
{
  "jsonrpc": "2.0", "id": 2, "method": "tools/list"
}
// ARTEMIS returns all 5 tools with full JSON Schema
{
  "result": {
    "tools": [
      {
        "name": "mobile_run_task",
        "description": "Run a natural language task on Android",
        "inputSchema": {
          "properties": {
            "task": { "type": "string" },
            "profile": { "enum": ["flash", "pro"] }
          },
          "required": ["task"]
        }
      }
      // + 4 more tools...
    ]
  }
}
ToolWhat it does
mobile_run_taskRun a natural language task on the device
mobile_manage_taskCheck status, pause, or cancel a running task
mobile_get_device_stateGet current screenshot + UI tree
mobile_inspect_traceGet full history of actions + screenshots
mobile_diagnoseGet Logcat output + device diagnostics
▶️ Step 3 — Execution (tools/call)
json-rpc — full call + response
// Claude Code calls mobile_run_task
{
  "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": {
    "name": "mobile_run_task",
    "arguments": {
      "task": "Login with test@app.com, verify dashboard",
      "profile": "flash"
    }
  }
}
// During execution — progress notifications (no id!)
{
  "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "progress": 4, "total": 12,
               "message": "Tapping login button..." }
}
// Final response
{
  "jsonrpc": "2.0", "id": 7,
  "result": {
    "content": [
      { "type": "text",
        "text": "Login succeeded. Dashboard loaded." },
      { "type": "image", "data": "iVBOR...",
        "mimeType": "image/png" }
    ],
    "isError": false
  }
}
🔌 Step 4 — Transport: stdio vs HTTP

stdio (ARTEMIS default)

Claude Code spawns ARTEMIS as a child process. Communication is via stdin/stdout — every message is one JSON line ending in \n. No network overhead. Fastest for local tools.

# ARTEMIS spawned by Claude Code
python -m artemis.mcp_server

Streamable HTTP (remote)

For remote MCP servers. Client sends HTTPS POST requests. Server streams responses via SSE (Server-Sent Events). Not used by ARTEMIS locally.

Section 07

ARTEMIS & Flutter UIs

Flutter renders everything on a single GPU canvas — which means Android can't see any UI elements by default. Here's how ARTEMIS handles that.

❌

Native Android App

Every widget is a real Android View object. UIAutomator dumps the full hierarchy — every button, text field, and label is discoverable.

// Android sees everything
<TextView> Login Title
<EditText> Email Field  ← clickable
<EditText> Password     ← clickable
<Button>   Sign In      ← clickable
⚠️

Flutter App (without Semantics)

Flutter draws everything on a single GPU texture. Android sees only one opaque surface — no buttons, no text fields, nothing.

// Android sees nothing useful
<FlutterView>
  /* empty — GPU canvas */
</FlutterView>

The Solution: Flutter AccessibilityBridge

🧩

Flutter Widget Tree

Your Dart widgets: Column → Text → TextField → ElevatedButton

🔀

Flutter Semantics Tree (Dart)

Flutter Engine builds a parallel tree of SemanticsNode objects describing every interactive element — label, role, bounds, callbacks.

🌉

AccessibilityBridge

Translates each SemanticsNode into an Android AccessibilityNodeInfo object — exactly what UIAutomator and ARTEMIS expect.

✅

ARTEMIS Reads Normally

ARTEMIS sees <node text="Sign In" class="android.widget.Button" clickable="true"/> — same as a native app.

⚠️

Semantics are NOT enabled by default in Flutter

The Semantics Tree is only built when TalkBack (screen reader) is active on the device, OR when your code explicitly requests it. Without it, ARTEMIS falls back to visual mode — slower and less accurate.

How to Enable Semantics for ARTEMIS

dart — main.dart
void main() {
  WidgetsFlutterBinding.ensureInitialized();

  // Enable Semantics Tree in debug builds only
  assert(() {
    SemanticsBinding.instance.ensureSemantics();
    return true;
  }());

  runApp(MyApp());
}

Making Flutter Widgets ARTEMIS-Friendly

dart — semantics best practices
// Level 1: Standard widgets — automatic semantics
Text("Login")              // label = "Login"
ElevatedButton(...)        // isButton = true
TextField(hint: "Email")  // isTextField = true

// Level 2: Custom widgets — use Semantics wrapper
Semantics(
  label: 'Product Card: iPhone 15',
  hint: 'Double tap to view details',
  button: true,
  child: GestureDetector(
    onTap: () => navigateToProduct(),
    child: CustomProductCard(product: product),
  ),
)

// Level 3: Add identifier for reliable ARTEMIS targeting
Semantics(
  identifier: 'login-button',  // → resource-id in tree
  label: 'Sign In',
  button: true,
  child: ElevatedButton(
    onPressed: onLogin,
    child: Text('Sign In'),
  ),
)
// ARTEMIS now sees: resource-id="com.app:id/login-button"
Section 08

Pro Mode — Multi-Agent Architecture

For complex, long-running tasks (30+ steps) that require planning, verification, and automatic recovery from failures.

💡

Why Pro Mode Exists

Flash fails on long tasks because it has no plan to refer back to, no way to verify milestones, and no structured recovery when something unexpected happens. Pro Mode adds a 3-agent system that handles all of this.

Agent 1

🗺️ The Planner

  • Creates a full Markdown execution plan
  • Defines milestones (checkpoints)
  • Adds expected outcomes per step
  • Defines fallback strategies
  • Updates plan if environment changes
Agent 2

⚙️ The Operator

  • Executes steps from the plan
  • Runs pre-action verification before every tap
  • Auto-dismisses popups and interruptions
  • Opens "Execution Incidents" on failure
  • Attempts multiple recovery strategies
Agent 3

✅ The Checker

  • Read-only — never touches the device
  • Verifies milestone completion
  • Triggers rollback if verification fails
  • Writes the final execution report
  • Configurable: off / final / checkpoints / strict

What the Planner Produces

markdown — planner output
# Execution Plan: Complete Checkout Flow Test

## Milestones
- [ ] M1: 5 products browsed
- [ ] M2: Cart has 3 items
- [ ] M3: Promo code applied
- [ ] M4: Payment submitted
- [ ] M5: Order confirmed

## Steps

### Phase 1: Browse
- [ ] Step 1: Open app, verify product grid visible (min 5 items)
  - Expected: Grid with product cards
  - Fallback: If empty → scroll down, wait 3s, retry

- [ ] Step 7: Add Product 1 to cart
  - Expected: Cart badge shows "1"
  - Verify: cart_count == 1

## Recovery Protocols
- On crash: restart app, resume from last completed milestone
- On popup: dismiss and continue
- On timeout: screenshot + retry step once

Pre-Action Verification (Operator)

📋

Plan says: Tap "Add to Cart" at index 5

The Operator reads the current step from the shared plan.

🔍

Pre-check: Is index 5 in the current tree?

Reads the live accessibility tree. If the element is there — proceed. If not — open recovery flow.

🔄

Recovery: Search by text, then visual

Tries search_by_text("Add to Cart"), then visual search from screenshot. If found — tap. If not — opens an Execution Incident.

✅

Continue or escalate

If recovered — continues from where it left off. If all strategies fail — incident is logged and Checker is notified.

Shared State — How Agents Communicate

The three agents don't call each other directly. They communicate through a shared state object that all three can read/write. Planner writes to the plan section. Operator writes to execution. Checker writes to verification. Each agent only has write access to its own section.

Section 09

Using ARTEMIS: APK vs Source Code

Two ways to use ARTEMIS — and how they combine for maximum power.

📦

Black Box — APK Only

You give ARTEMIS a compiled APK and task. It tests the app from the outside exactly like a real user would. It sees UI elements and Logcat — nothing else.

# Install APK on device
adb install my_app.apk

# Give ARTEMIS a task
"Login with test@email.com / pass123,
 verify dashboard loads correctly"

Best for: release testing, testing third-party apps, regression testing after build.

💻

White Box — With Source Code

Claude Code sees your source code AND ARTEMIS sees the device. Together they can build, test, find bugs, fix them, and test again — fully automated.

You tell Claude Code:
"Build the APK and test login, fix any bugs"

Claude Code:
1. flutter build apk --debug
2. mobile_run_task("install + test login")
3. ARTEMIS: "button not responding"
4. Claude finds bug in code
5. Fixes it, rebuilds, retests

Best for: active development, CI/CD with auto-fix, complete build-test-fix loops.

💡

Flutter-specific tip: Enable Semantics in your debug build

When using ARTEMIS with your Flutter source code, add SemanticsBinding.instance.ensureSemantics() to your debug build configuration. This ensures ARTEMIS uses the fast accessibility tree path instead of the slower visual fallback for every interaction.

Writing Effective Task Prompts

There's no required format — but how you write your task directly affects accuracy, speed, and token cost.

💡

No Special Syntax Required

ARTEMIS reads plain natural language. No brackets, no XML, no special keywords. But the way you describe the task significantly impacts how many turns it takes — and turns = tokens = cost.

The 5 Golden Rules

01

Describe outcomes, not steps

Tell ARTEMIS what you want to achieve. It will figure out how to get there on its own.

02

Use concrete values

Always provide exact emails, passwords, names, and search terms. Never say "test credentials".

03

End with a verification

Always state what success looks like: "verify dashboard loads" or "confirm the name appears on screen".

04

Split big tasks

3 Flash tasks are faster and cheaper than 1 Pro task. Split anything over 15 steps.

05

Skip explaining your app

ARTEMIS sees the screen in real time. Don't describe your UI structure — it will find elements itself.

Token Costs — How They're Calculated

Your task prompt is the smallest cost. Here's what actually drives token usage — and how to minimize it.

What Makes Up Each Turn's Token Cost

UI Tree (XML)
~2,500 tok
Screenshot
~1,200 tok
History
~1,000 tok
System Prompt
~600 tok
Your Task
~20 tok
Output (action)
~80 tok
💡

Key insight: Your task text barely matters for cost

Writing a 200-word task vs a 10-word task changes your cost by less than 1%. The real cost drivers are the UI Tree and screenshot sent every single turn. Reduce turns, not task length.

Tokenization Rules

Content TypeApproximate Token Ratio
English text1 token ≈ 4 characters / 0.75 words
Arabic text1 token ≈ 1–2 characters (more expensive!)
XML / Code1 token ≈ 3–4 characters
Screenshot (base64)~800–2,000 tokens depending on resolution

Summary: The Golden Rules for Token Efficiency

1

Reduce turns, not task length

Each turn costs ~5,000–8,000 tokens regardless of your task text. Every extra turn you eliminate saves more than shortening your prompt.

2

Use Flash for short tasks

Flash (3–5s/step) vs Pro (15–40s/step). Use Pro only when you need it — it uses 5–10× more tokens per task.

3

Enable Flutter Semantics

Visual fallback (no semantics) = more turns per action, because coordinate targeting is less precise and needs more retries.

4

Split large tasks

3 × 10-step Flash tasks use fewer tokens than 1 × 30-step Flash task, because history compression kicks in later and is less efficient.

How to Use Traces for Debugging

1

Test fails in CI — get the trace_id

Your pytest output shows: Trace: artemis trace flash-abc123-def456. This is your entry point.

2

Open in Web Console

Run artemis trace flash-abc123-def456 — opens the replay in your browser. Navigate turn by turn.

3

Find the failing turn

Look for the turn where the action changed from success to something unexpected. Check the screenshot_before to see what the agent was looking at.

4

Check Logcat at that moment

The trace includes timestamped Logcat — see exactly what your app was doing in the background at the same moment the agent was confused.

5

Fix the task or the app

Either your task wording was ambiguous (fix the prompt) or your app had a bug (fix the code). Rerun to confirm.

What Gets Sent to the Cloud (by default)

Every turn, ARTEMIS sends your device's screenshot and UI tree XML to the vision LLM API (Gemini/Claude/OpenAI). If your app displays sensitive user data, this data appears in those screenshots and is sent to Google/Anthropic/OpenAI servers. Use a test account with dummy data in CI, or switch to a local model.

Security Best Practices

1

Always use a dedicated test account

Never run ARTEMIS against production accounts. Create a separate test account with dummy data. Assume every screenshot is sent to the cloud.

Store API keys in environment variables only

Add artemis-traces/ to .gitignore

4

Appium's main advantage is cross-platform — you write tests in JavaScript/Python/Ruby and run them on both Android and iOS with minimal changes. It's the industry standard for teams that need one test suite for multiple platforms.

✅

Best for

Teams that test both Android AND iOS. Existing Selenium/WebDriver expertise. QA teams that don't write Kotlin. Enterprise projects with large existing Appium suites.

❌

Don't use when

Flutter apps (Appium Flutter plugin is fragile). Tests keep breaking on minor UI updates. Long complex workflows (flakiness compounds). You want fast setup and low maintenance.

🤖 Use ARTEMIS when…

ARTEMIS shines in scenarios where traditional tools are painful: Flutter apps, fast-changing UIs, complex workflows, and situations where you want tests that are readable by anyone on the team.

✅

Flutter apps. UIs that change frequently. E2E flows spanning multiple screens. Teams without dedicated QA engineers who write Kotlin. Tasks you want to describe in plain English. ⚠️

Consider carefully when

You need sub-second test execution (ARTEMIS is 3–5s/step). Your app shows sensitive PII in the UI (use local model or dummy data). Cost per test matters at very high volume (>10,000 runs/day). You need to test animations precisely or frame-perfect timing.

The Hybrid Approach (Recommended)

The best teams don't pick one tool — they use all three strategically:

1

Espresso / flutter_test for unit-level UI

Fast, runs in-process, tests individual widgets and screens in isolation. Hundreds of these run in seconds.

2

ARTEMIS Flash for smoke tests on every PR

5–10 key user journeys that verify the app basically works. Runs in ~5 minutes, catches regressions fast.

3

ARTEMIS Pro for full E2E regression on main

Complete flows: onboarding, checkout, settings, edge cases. Runs on every merge to main with full reporting.

The rules.md File — Teaching Claude Code How to Use ARTEMIS

There are TWO AI systems involved. rules.md is the rulebook sent to the outer AI (Claude Code / Cursor) — not to ARTEMIS itself. It tells your IDE's AI assistant how to behave when driving Android devices.

🤖

Inner AI — ARTEMIS Agent

The vision LLM (Gemini/Claude) running inside ARTEMIS. Decides each individual action on screen (tap, type, swipe). Gets its instructions from ARTEMIS's internal system prompt. You don't configure this directly.

🧠

Outer AI — Claude Code / Cursor

The AI assistant in your IDE. Decides when to call ARTEMIS, what task to give it, and which profile to use. This is what rules.md configures.

💡

Where rules.md Lives

When you run ./start.sh, ARTEMIS offers to install rules.md into your AI IDE automatically. For Claude Code it goes to ~/.claude/rules/artemis.md. For Cursor: .cursorrules. For Codex: ~/.codex/AGENTS.md. The README marks this as highly recommended — skip it and your outer AI won't know how to use ARTEMIS correctly.

What rules.md Covers

🗺️ Rule 1 — Active Exploration Before Coding

Before writing any code or building an APK, Claude Code should explore the app first using mobile_get_device_state to understand what's currently on screen, what flows exist, and what UI elements are available.

rule — explore first
// What Claude Code does WITHOUT the rule:
You: "Test the login flow"
Claude: "I'll build the APK and test it."
// Builds APK → installs → runs task → might get wrong screen

// What Claude Code does WITH the rule:
You: "Test the login flow"
Claude: mobile_get_device_state()  ← first looks at what's on screen
// Sees current state → understands context → then acts intelligently
⚡ Rule 2 — Flash vs Pro Routing Strategy

The rule gives Claude Code an explicit decision tree for choosing profiles — so it doesn't always default to Flash or always use Pro unnecessarily.

rule — profile routing
Use FLASH when:
- Task is clear and specific (login, tap a button, verify text)
- Estimated steps < 15
- Quick smoke test or single-screen verification
- Speed matters (CI/CD smoke test)

Use PRO when:
- Task spans multiple screens or apps
- Estimated steps > 20
- Needs verification at multiple points
- Long-running exploration or stability test
- Any task involving payment, checkout, or complex state
⏱️ Rule 3 — Latency and Timing Compensation

Tells Claude Code to account for real device timing. Apps need time to load, animations need time to complete, keyboards need time to appear. The rule prevents Claude Code from sending back-to-back tasks too fast.

rule — timing awareness
// Bad — Claude Code sends next task immediately
await artemis.run("Install the APK")
await artemis.run("Open the app")  ← might run before install finishes

// Good — rule teaches Claude to chain properly
await artemis.run(
  "Install the APK, wait for it to complete, "
  "then open the app and verify main screen loads"
)  ← single task handles the sequence
🎯 Rule 4 — Dynamic-First, Coordinate-Fallback

Teaches Claude Code to always prefer element-based targeting (by text, resource-id, index) over coordinate-based targeting when writing task prompts. Coordinates break when screen size changes; element references don't.

rule — locator preference
// ❌ Coordinate-based (breaks on different screen sizes)
"Tap at coordinates (540, 1200)"

// ✅ Dynamic element-based (works on any screen size)
"Tap the Sign In button"
"Tap the button with text 'Sign In'"
"Tap the element with id 'login-button'"
⚠️

Install rules.md in ONE place only

Claude Code loads both ~/.claude/CLAUDE.md and ~/.claude/rules/*.md. If you install rules.md in both locations, it gets loaded twice — wasting context tokens every single turn. The installer handles this correctly, but if you add it manually, pick one location only.

Terminal Mode — No IDE Required

ARTEMIS works completely standalone from the terminal. No Claude Code, no Cursor, no MCP — just a command and a device.

💡

When to use Terminal Mode

Scripting tasks in bash/shell. Running one-off tests quickly without opening an IDE. Cron jobs that run tests on a schedule. Debugging a specific task interactively. CI/CD pipelines where you call ARTEMIS directly, not via pytest.

All Terminal Commands

bash — complete terminal reference

Real-world Terminal Scripting Examples

🔁 Nightly Regression Script (bash)
bash — nightly_tests.sh
#!/bin/bash
set -e

# Build latest APK
flutter build apk --debug
uv run artemis install build/app/outputs/flutter-apk/app-debug.apk

# Run smoke tests
TASKS=(
  "Open app, verify main screen loads without errors"
  "Login with test@app.com / Pass123, verify dashboard"
  "Navigate to profile, verify user name shows correctly"
  "Open settings, verify notifications toggle is visible"
)

PASS=0; FAIL=0

for task in "${TASKS[@]}"; do
  if uv run artemis run "$task" --profile flash; then
    echo "✅ PASS: $task"
    ((PASS++))
  else
    echo "❌ FAIL: $task"
    ((FAIL++))
  fi
done

echo "Results: $PASS passed, $FAIL failed"
exit $FAIL

Analytics QA — A Different Use Case

ARTEMIS isn't just for UI testing. Teams use it to verify that analytics events (Firebase, custom datalayers) fire correctly with the right parameters — automatically.

The Problem ARTEMIS Solves for Analytics

Verifying mobile analytics manually means: tap through a checkout funnel on a test phone, watch Charles Proxy or Logcat line by line, verify that purchase_completed fired with the correct parameters, and pray nothing broke in the data layer. One minor UI update breaks your entire verification process.

How It Works for Analytics

▶️

ARTEMIS navigates the funnel

"Open the app, add Product X to cart, apply promo code TEST2026, and complete guest checkout."

📋

Logcat captures all events in real-time

As ARTEMIS navigates, it streams Logcat — capturing every Firebase debug event, SDK payload, and custom datalayer event with timestamps.

🔍

Verify events fired correctly

After the run, inspect the trace's Logcat for your analytics events — check they fired at the right step with the right parameters.

🔁

Run edge cases automatically

Pro Mode can run 10-hour exploratory passes to trigger non-linear user journeys and catch missing event parameters across edge cases.

Analytics QA in Code

python — verify firebase events
@pytest.mark.asyncio
async def test_purchase_event_fires(artemis):
    """Verify purchase_completed event fires with correct params."""

    result = await artemis.run(
        "Open app, add 'iPhone Case' to cart, "
        "checkout as guest with card 4111111111111111, "
        "complete the purchase, verify order confirmation shows",
        profile="pro"
    )
    assert result.succeeded

    # Get the Logcat from the trace
    trace = await artemis.get_trace(result.trace_id)
    logcat = "\n".join(trace.logcat)

    # Verify the analytics event fired
    assert "purchase_completed" in logcat, \
        "purchase_completed event never fired!"

    # Verify required parameters are present
    assert "item_name: iPhone Case" in logcat
    assert "currency: EGP" in logcat
    assert "transaction_id:" in logcat  # any value is fine

    # Verify NO double-fire (common bug)
    purchase_count = logcat.count("purchase_completed")
    assert purchase_count == 1, \
        f"purchase_completed fired {purchase_count} times (expected 1)!"

@pytest.mark.asyncio
async def test_screen_view_events(artemis):
    """Verify screen_view fires for every major screen."""

    result = await artemis.run(
        "Login, navigate to: Home → Products → Product Detail → Cart → Profile",
        profile="pro"
